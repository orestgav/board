# AI INSTRUCTIONS — DnD Campaign Knowledge Base

Ти працюєш з базою знань DnD кампанії у форматі Markdown-файлів у VS Code workspace.

## 1. Як читати структуру

- Кожен файл = одна сутність (NPC, локація, сесія тощо)
- Метадані знаходяться у YAML-блоці на початку файлу
- Основний контент — структурований секціями (##)

## 2. Типи файлів

- type: player — персонажі гравців
- type: npc — неігрові персонажі
- type: location — місця
- type: world — глобальний лор
- type: faction — фракції (країни, організації, культи, гільдії)
- type: session — записи сесій
- type: creature — статблоки
- type: item — предмети
- type: encounter — сутички
- type: ai-context — службові файли для AI

## 2a. Куди кладеться новий файл

Кожна тека розкладена по підпапках. **Файл у корені теки — помилка.**

| Тека | Розкладка |
|---|---|
| `world_data/npcs/` | за місцем; окремі групи (екіпаж, банда, рідня гравців) — своїми підпапками |
| `world_data/locations/` | держава -> місто -> заклади: `<держава>/<місто>.md`, `<держава>/<місто>/<заклад>.md`. Файл у теці держави = точка на карті, підтека з назвою міста = що всередині нього |
| `world_data/items/` | `party/` (спільне майно й улики), `pc/` (особисті предмети гравців), `world/` (не в партії) |
| `world_data/factions/` | за державами, плюс окремі полиці для місцевих банд і божественних сил |
| `world_data/world/` | `regions/` — землі, `lore/` — явища; `timeline.md` лишається в корені |
| `world_data/bestiary/` | за родом: `humanoids/`, `monsters/`, `fiends/`, `celestials/`, `undead/`, `named/` |

- Конкретних полиць (держав, міст, груп) у кампанії ще немає — вони заводяться разом із першими картками, **за погодженням з ДМом**.
- Підпапка — це полиця, а не факт про світ. Якщо NPC переїхав у грі, картка може переїхати в іншу підпапку; лінки `[[слаг]]` від цього не ламаються.
- Якщо сутність не лягає в жодну полицю — **спитай ДМа**, куди її класти. Не заводь нову підпапку сам і не клади файл у корінь.

## 2b. Картинки

- У `examples/maps/` лежать референсні приклади стилістики бойових карт. Під час створення нових карт використовуй їх як візуальний орієнтир.
- Для бойових карт використовуй дюймову сітку з такими стандартними параметрами: крок — **1 дюйм**; колір ліній — **RGB `(5, 7, 9)`** (`#050709`); альфа — **165/255** (приблизно **65% непрозорості**); товщина — **10 px при 300 DPI** (приблизно `DPI / 30` px або `0,033″` за іншої роздільної здатності). Накладай сітку після генерації арту, щоб її геометрія й друкарський масштаб були точними.
- **За замовчуванням усі нові арти генеруються у співвідношенні сторін 1:1.** Інше співвідношення використовуй лише за прямою вказівкою ДМа або коли формат однозначно заданий призначенням конкретного зображення.
- **Арти NPC:** генеруй у співвідношенні **3:4, вертикаль**.
- **Арти монстрів:** генеруй у співвідношенні **3:4, вертикаль**, із прозорим фоном.
- **Арти локацій і широких сцен:** генеруй у співвідношенні **3:2, горизонталь**.
- **Арти предметів:** предмет показано цілком на переважно білому тлі, без персонажів, декорацій, рамок, підписів чи водяних знаків. За предметом має бути дуже ледь помітна, розмита пастельна пляма; її колір відповідає `rarity` предмета. Пляма не є сценою, німбом або різкою тінню й не має переважати над білим тлом. Орієнтуйся на подачу предметних ілюстрацій у *Player’s Handbook* і *Dungeon Master’s Guide*: виразна форма, стримана ручна мальовка, чиста предметна композиція.
- Для історичної зброї, обладунку й речей із реальним прототипом перед генерацією звіряй конструкцію та пропорції з надійними музейними або профільними джерелами. У prompt явно фіксуй визначальні конструктивні деталі з опису картки; не підмінюй їх довільним фентезійним дизайном.
- **Арти персонажів за замовчуванням кадруй приблизно по пояс.** Крупний портрет або повний зріст використовуй лише тоді, коли цього потребує задум чи прямо просить ДМ.
- Лежать у `_media/`: `npcs/`, `locations/`, `items/`, `creatures/`, `maps/`, `initiative-tokens/`.
- **Маркер ініціативи для ворога.** Для кожного статблоку ворога поряд із головним артом готуй окремий маркер. Порядок роботи:
  1. Візьми основний арт істоти, збережи її впізнавані риси й помісти на суцільне біле тло `#FFFFFF` без тексту, тіні, рамки або декорацій.
  2. Зроби вертикальний макет **17 × 63 мм**. За 300 DPI це **201 × 744 px**. Істота має бути по центру й трохи меншою за висоту макета: залишай вузькі білі поля зверху та знизу. Не залишай навмисних білих смуг уздовж лівого й правого країв; руки, щупальця або корпус можуть торкатися краю чи трохи обрізатися.
  3. Збережи маркер як WebP q90 у `_media/initiative-tokens/` під назвою `<слаг>-token.webp`.
  4. У YAML статблоку додай `initiative_token: <слаг>-token.webp`.
  5. Перевір готовий WebP візуально й запусти `node tools/validate.mjs`.
  6. **Не створюй PDF автоматично.** PDF для друку роби лише після окремого запиту ДМа, який містить перелік маркерів. Тоді збери їх на аркушах **A4, 300 DPI** (`2480 × 3508 px`), кожен у точному розмірі **201 × 744 px**, з тонкими сірими контурами для вирізання. Клади файл у `print/initiative-tokens/` і друкуй у масштабі **100%**, без «підігнати до сторінки».
- **Формат — тільки WebP**, зокрема для артів із прозорим фоном (WebP тримає альфу). Кинутий PNG/JPG перед записом у `_media/` конвертуй у WebP: портрети й арти q82, карти q90; оригінал поруч не зберігай. Кожен завершений арт треба покласти у відповідну підпапку `_media/` як WebP і вказати його імʼя в полі `image:` картки. Локального конвертера нема — став `sharp` через npm у scratch-теку. `validate.mjs` попереджає про не-WebP файли.
- Імʼя файлу = слаг картки (`<слаг>.webp` для `<слаг>.md`); спільна сцена — `<слаг-1>-<слаг-2>.webp`; друга картинка — `<слаг>-2.webp`.
- У YAML: `image: <слаг>.webp` — **тільки імʼя файлу**, без шляху.
- Якщо гравці знають сутність, але ще не бачили її вигляду, додай `image_known: false`: приватна картка збереже `image`, але гравцям портрет не показують. Коли герої побачать сутність, зміни на `image_known: true` або прибери прапорець.
- Для `type: location` карта задається окремо: `map: <слаг>-map.webp` — файл з `_media/maps/`. Поле `image:` завжди лишається головною ілюстрацією.
- Якщо є розмітка карти, `map_data: <слаг>-map.json` посилається на JSON у кореневій теці `map-data/`: полігони районів і координати обʼєктів задані у відсотках `0–100` від верхнього лівого кута.
- У тілі картки: `![Назва](../../../_media/npcs/<слаг>.webp)` — звичайний Markdown із відносним шляхом (кількість `../` = глибина картки).
- `![[<слаг>.webp]]` **не використовуємо**: Обсидіана в проєкті нема, у VS Code і на GitHub це не видно.
- Картинки додає ДМ. Сам не вигадуй імен неіснуючих файлів — `node tools/validate.mjs` на цьому впаде.

## 2c. Секція `## Звʼязки` в картці

У картці є секція `## Звʼязки`, де лінки згруповані за типом сутності:

```markdown
- NPC: [[slug]], [[slug]]
- Фракції: [[slug]]
- Статблоки: [[slug]]
- Предмети: [[slug]]
- Сесії: [[slug]]
- Локації: [[slug]]
```

- Рядки ставляться **за потреби** — не обовʼязково всі. Нема звʼязку такого типу — рядка просто нема.
- Лінкуємо **тільки наявні** картки. Якщо потрібної сутності в базі ще нема — це не привід завести її самовільно чи вигадати: спитай ДМа.
- Лінки двосторонні: якщо в локації стоїть NPC, то в картці NPC у `## Звʼязки` має бути ця локація.
- У локації рядки `NPC:` і `Предмети:` — це те, що кнопка «Локація» на дошці кладе всередину рамки. Статблоки беруться **тільки з наявних** карток `world_data/bestiary/`; якщо нічого не підходить — спитай ДМа, а не вигадуй істоту.

## 2d. Нотатки на дошці

Коли ДМ просить **додати на дошку важливе нотатками**, оформлюй матеріал як швидку шпаргалку для ведення сесії:

- Розділи матеріал на **окремі тематичні картки** за ходом сцени: прибуття, свідок, розмова, відкриття, наслідки тощо.
- Перша строка кожної нотатки — **коротка назва жирним шрифтом**. Не використовуй для назви `#`, `##` або `###`.
- Після назви — лише **короткі тези-буліти**; одна думка на один рядок.
- У кожній тезі виділяй **жирним опорні слова, імена, числа, умови, рішення й наслідки**.
- Залишай дослівно тільки **окремі фрази-якорі**, які ДМ може одразу сказати за столом.
- Не пиши довгих абзаців і художнього переказу: нотатку мають розуміти **з одного швидкого погляду**, а решту ДМ скаже своїми словами.
- Розкладай картки в логічному порядку й **усередині рамки потрібної локації або сцени**, не перекриваючи наявні елементи.
- Важливу приховану інформацію позначай коротко: **DM**, **Пастка**, **Наслідок** або `⚠️`.
- Бери факти з наявного канону. Якщо потрібної деталі немає, познач її як **не визначено**, а не вигадуй.
- Опис зовнішності NPC, його поведінку та манеру мовлення винось у секцію `## На дошці` самої NPC-картки; не дублюй це окремою нотаткою без потреби.

## 3. ГОЛОВНЕ ПРАВИЛО: не вигадувати у файлах

**Ніколи не записуй у файли власні здогади, припущення чи ідеї. Завжди спершу запитай.**

- У файли потрапляє лише те, що сказав ДМ, або те, що вже є в базі.
- Якщо бракує факту — залиш «не визначено» і спитай. Не заповнюй прогалину правдоподібним варіантом.
- Свої ідеї, версії та пропозиції озвучуй **у відповіді, а не у файлі**. ДМ вирішить, що з них стає каноном.
- Це стосується й секцій «Відкриті питання»: туди йдуть питання ДМа, а не твої гіпотези.
- Причина: файл виглядає як канон. Здогад, записаний у файл, через тиждень не відрізнити від факту.

## 3a. ТВОРЧА РОБОТА: спочатку обговорення, потім файли

> [!danger] ЖОДНИХ ТВОРЧИХ ПРАВОК ДО ЯВНОГО ПІДТВЕРДЖЕННЯ ДМа
> Коли ДМ просить придумати, розвинути, переробити або доповнити персонажа, локацію, фракцію, предмет, сюжетну лінію чи іншу сутність, це **запрошення до обговорення, а не дозвіл одразу редагувати файли**.

Обовʼязковий порядок роботи:

1. Прочитати повʼязаний контекст у режимі лише читання.
2. Запропонувати ідеї **в чаті**: основну концепцію, варіанти й важливі наслідки для наявного лору.
3. Дочекатися **явного підтвердження ДМа**, що саме з пропозиції стає каноном. Мовчання, позитивний тон або прохання «давай придумаємо» не є таким підтвердженням.
4. Лише після підтвердження внести схвалений варіант у файли.

- Якщо в процесі виявилася нова творча розвилка, якої не було в погодженій пропозиції, **зупинити редагування й повернутися до обговорення**.
- Пряме прохання на кшталт «внеси цей уже погоджений текст у файл» або «виправ цю конкретну помилку» саме є дозволом на відповідну точкову правку; повторне підтвердження не потрібне.

Мета цього порядку — не перетворювати непогоджену ідею на канон і не змінювати туди-сюди десятки залежних файлів.

## 3b. ТЕКСТ ДЛЯ ГРАВЦІВ: краще недописати, ніж заспойлерити

Гравцям призначено текст **тільки** з трьох місць:

- `## Публічна довідка` у картці сутності;
- поле `Гравцям:` у [[active-quests]];
- рядки без 🔒 у [[timeline]].

Усе інше — DM-інформація: callout-блоки (`>`), рядки з 🔒, секції «Не визначено», «DM», «Відкриті питання», «Звʼязки».

Генератора публічного сайту в цьому репозиторії поки немає. Правила нижче діють однаково: цей текст готується для гравців.

**Правило: якщо вагаєшся, чи гравці це знають — не пиши.** Недописане можна додати після наступної сесії; винесений спойлер не повернеш.

### Жодної правки довідки втиху

**Щоразу, коли ти створюєш або змінюєш секцію `## Публічна довідка` — покажи ДМу повний текст того, що написав, просто у відповіді.** Не «оновив довідку в трьох картках», а сам текст, картка за карткою.

- Це стосується і нової довідки, і правки одного речення, і перенесення тексту з іншої секції.
- Причина: це **єдине**, що бачать гравці. Помилку в ДМівській секції можна виправити наступного тижня, а спойлер, який уже прочитали, не забереш.
- Якщо правок багато — усе одно покажи всі. Довгу відповідь прочитати можна, мовчазний спойлер — ні.
- Те саме стосується поля `Гравцям:` у [[active-quests]] і рядків без 🔒 у [[timeline]].

Як писати довідку: суцільним текстом, літературно, **«герої», а не «вони»**. З контекстом і супутньою інформацією, а не одним рядком. Листи — детально, з текстом.

Прапорці у frontmatter, які знімають сутність із тексту для гравців:

| Прапорець | Коли ставити |
|---|---|
| `secret: true` | сутність узагалі таємна |
| `pc_known: false` | партія про неї ще не знає |
| `public: false` | **персональний бекграунд одного гравця** (рідня, наставники, особисті предмети) або службовий файл. Гравець знає, решта партії — ні, тож до спільного тексту це не йде |

Типи `player`, `session`, `creature`, `encounter`, `ai-context` гравцям довідкою не показуються взагалі.

## 4. Обов’язкові правила

1. Завжди використовуй існуючі файли, якщо сутність уже існує — не дублюй її
2. Завжди створюй нові сутності як окремі файли — у правильній підпапці (див. 2a)
3. Дотримуйся існуючих шаблонів з `_templates/`
4. Не змінюй структуру YAML без потреби
5. Не видаляй інформацію — тільки доповнюй або уточнюй
6. Після кожної сесії онови `## Публічна довідка` тих сутностей, про які партія дізналася нове

## 5. Лінки між сутностями

- Використовуй формат: `[[назва-файлу]]` (kebab-case, без шляху й розширення)
- Завжди додавай зв’язки між NPC, локаціями і подіями
- Якщо створюєш нову сутність — одразу лінкуй її

## 6. Робота з контекстом

Перед відповіддю:
- Орієнтуйся на файли в /ai-context/
- Особливо:
  - `world_data/world/timeline.md` — хронологія, **джерело істини по подіях**
  - `current-state.md` — де партія зараз і що в неї на руках
  - `active-quests.md` — квести; поле `Гравцям:` — текст для гравців
  - `loose-threads.md` — наслідки й борги
  - `dm-plans.md` — те, що ще **не сталося**, у масштабі кампанії
  - `next-sessions.md` — **плани кількох найближчих сесій**: де стартуємо, очікувані сцени, рейки та що готове до столу. Після кожної гри зігране переноситься в `world_data/sessions/`, а решта плану уточнюється. Болванка — `_templates/sessions-plan.md`
  - `important-npcs.md` — індекс фігур

Якщо інформації не вистачає — явно вкажи це

## 7. Стиль запису

- Пиши коротко і по суті
- Без художньої води, якщо не просять
- Структуровано
- Межу «що відомо гравцям» тримає **одна** секція на картку:
  - картка для гравців -> `## Публічна довідка` (зв'язний текст для гравців);
  - картка знята прапорцем (`public: false`, `secret: true`, `pc_known: false`) -> `## Що знають гравці` (буліти для ДМа).
- Обидві секції в одній картці **не тримаємо** — це дублювання, яке швидко розходиться між собою.
- Усе інше в сутності вважається DM-інформацією за замовчуванням.

### 8a. Як писати сесію в `timeline.md`

- **День сесії** — тезисні буліти з жирними опорними словами, **орієнтовно 600–700 слів** на день. Не літературні абзаци й не стислий перелік на кілька речень.
- Згадуючи заклад, лінкуй і його господаря чи продавця.
- Без службових позначок на кшталт «⏸ сесія зупинилася тут».
- **Сцена-відкриття** — окремий рядок у таблиці «Паралельно з кампанією»: зв'язний переказ сцени з ключовими репліками, **орієнтовно 200–250 слів**.
- Рядки без 🔒 — текст для гравців: покажи його ДМу (п. 3b).
